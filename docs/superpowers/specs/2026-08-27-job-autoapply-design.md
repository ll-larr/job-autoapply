# Система полуавтоматической подачи резюме

**Дата:** 2026-08-27
**Статус:** дизайн утверждён пользователем, реализация не начата

---

## 1. Задача

Артём ищет работу бизнес-аналитиком (junior+/middle). Резюме переписано под ATS 2026-08-25, лежит в `C:\Users\lar\Desktop\Резюме\`, собирается генератором из `_generator/content.js`. Прежняя проблема — отклики не доходили: ручная подача медленная, а массовая шаблонная рассылка читается как спам.

Нужна система, которая берёт на себя механику (поиск, скоринг, черновик письма, отправка), но оставляет человеку решение по каждому отклику.

## 2. Границы

**В скоупе первой итерации:** ядро + адаптеры `hh.ru` и `hr.ge`.

**Во второй итерации:** `careerist.ru`, `geekjob.ru`, `careerspace.app`, `jobs.ge`/`remotejob.ru` (если подтвердится, что живы), фильтр `visa sponsorship / relocation` для США и Канады.

**Вне скоупа навсегда:**
- обход капчи любого вида;
- ввод и хранение паролей в коде или конфиге;
- полностью автономная отправка без подтверждения человеком.

## 5. Архитектура

### 5.1 Стек

- **Node.js 24 + TypeScript** — на машине стоит `v24.14.0`, npm `11.9.0`.
- **Playwright** — как зависимость проекта. Используется `launchPersistentContext` на выделенном профиле браузера.
- **SQLite** (`better-sqlite3`) — состояние очереди и история подач.
- **Anthropic SDK** (`@anthropic-ai/sdk`) — генерация врезок и полных писем.

Выбор Playwright обоснован: он уже используется в соседнем процессе (сборка PDF резюме), и `launchPersistentContext` решает задачу аутентификации без единого пароля в коде.

### 5.2 Модули

Каждый модуль имеет одну ответственность и тестируется отдельно.

**`core/vacancy.ts`** — единая модель вакансии, к которой приводят все адаптеры.

```
Vacancy {
  source: string          // 'hh' | 'hrge' | ...
  sourceId: string        // идентификатор в системе площадки
  title: string
  company: string
  url: string
  description: string     // полный текст для скоринга и письма
  salaryFrom, salaryTo, currency: nullable
  geo: string
  isRemote: boolean
  hasSponsorship: boolean // определяется по тексту, для 2-й итерации
  postedAt: Date
}
```

Зависимостей нет. Чистые типы и валидация.

**`adapters/<site>.ts`** — интерфейс ровно из двух методов:

```
interface Adapter {
  name: string
  search(filters: SearchFilters): Promise<Vacancy[]>
  apply(vacancy: Vacancy, letter: string): Promise<ApplyResult>
}

type ApplyResult =
  | { status: 'sent' }
  | { status: 'already_applied' }
  | { status: 'captcha' }        // останавливает всю очередь
  | { status: 'auth_required' }  // останавливает всю очередь
  | { status: 'failed', reason: string }
```

Ядро не знает, браузерный адаптер или HTTP. Новая площадка — новый файл, ядро не меняется. Это главная проверка дизайна: `hh` (Playwright) и `hrge` (HTTP) должны лечь в один интерфейс без исключений.

**`core/scorer.ts`** — скор вакансии против резюме. Правила, без LLM: дёшево, детерминированно, объяснимо. Веса по ключевикам из карты рынка, собранной 2026-08-25 (SQL, BPMN, UML, REST, Kafka, DWH/BI, LLM/AI, BRD/FSD/SRS, user story, CJM). Возвращает число 0–100 и список совпавших ключевиков — последний идёт в письмо.

Два порога, оба в конфиге:

- `MIN_SCORE` (стартовое значение 40) — ниже него вакансия отбрасывается и в очередь не попадает вообще. Письмо для неё не генерируется, деньги на LLM не тратятся.
- `LETTER_FULL_THRESHOLD` (стартовое значение 75) — на нём и выше письмо пишется в режиме `full`.

Стартовые значения — догадка. Калибруются на первой же живой выборке: система печатает распределение скоров по найденным вакансиям, пользователь смотрит, где реально проходит граница между «стоит подавать» и «мусор», и правит конфиг.

**`core/letter.ts`** — двухуровневая генерация.

- Режим `hybrid` (по умолчанию): берётся скелет из `templates/`, LLM пишет 2–3 предложения про конкретную компанию и стыкует опыт с требованиями. Вход ~1250 токенов, выход ~120.
- Режим `full` (скор ≥ порога): письмо пишется с нуля по тексту вакансии и резюме. Вход ~3000, выход ~350.

Модель `claude-opus-5`, `thinking: {type: "adaptive"}`. Резюме и инструкция стабильны между запросами и ставятся в начало промпта под `cache_control` — волатильная часть (текст вакансии) идёт после последнего брейкпоинта.

Оценка стоимости по ставкам Opus 5 ($5/1M вход, $25/1M выход) без учёта кэша: `hybrid` ≈ $0.009 за письмо, `full` ≈ $0.024. Сотня откликов в смешанном режиме — единицы долларов.

Скелеты (`templates/`) — творческий артефакт, пишет и утверждает пользователь. Стартовый набор: `fullstack-analyst`, `ai-llm-ba`, `product-ba`, `english-generic`.

**`core/queue.ts`** — SQLite. Таблица `applications`:

```
id, source, source_id, vacancy_json, score, letter, letter_mode,
status, created_at, decided_at, sent_at, error
status: pending | approved | skipped | sent | failed
```

Уникальный индекс на `(source, source_id)`. Это дедупликация: **на одну вакансию отклик не уходит дважды ни при каких условиях**, включая повторный запуск поиска и падение процесса посреди отправки.

**`ui/`** — локальная панель на `localhost`. Список карточек: слева вакансия (заголовок, компания, зарплата, скор, совпавшие ключевики, текст), справа письмо в редактируемом поле. Кнопки: одобрить, пропустить, сохранить правку. Массовые действия: одобрить всё выше порога, пропустить всё ниже.

Правки письма сохраняются в очередь и уходят именно в отредактированном виде.

**`core/sender.ts`** — забирает `approved` из очереди, вызывает `adapter.apply`, пишет результат.

### 5.3 Поток данных

```
адаптеры.search(filters)
        ↓
    dedupe по (source, source_id) против таблицы applications
        ↓
    scorer.score(vacancy)  →  отсев ниже MIN_SCORE
        ↓
    letter.generate(vacancy, score)  →  режим hybrid | full
        ↓
    queue.insert(status = pending)
        ↓
    ─── человек в панели: approve / skip / edit ───
        ↓
    queue(status = approved)
        ↓
    sender → adapter.apply → queue(status = sent | failed)
```

Границы стадий — записи в SQLite. Процесс можно убить в любой момент и перезапустить без потери и без дублей.

## 6. Защита аккаунта

Требования не опциональные, реализуются вместе с ядром.

1. **Троттлинг.** `MAX_PER_HOUR` и `MAX_PER_DAY` на площадку. Между отправками случайная пауза в заданном диапазоне. Счётчики хранятся в БД, переживают перезапуск.
2. **Капча — полная остановка.** `ApplyResult.status === 'captcha'` останавливает обработку очереди целиком, помечает текущую запись обратно в `approved` и уведомляет пользователя. Обход капчи не реализуется. Работа возобновляется только после того, как человек сам решил капчу в браузере.
3. **Пароли отсутствуют как класс.** Аутентификация — только через `launchPersistentContext` на профиле, куда пользователь залогинился руками. В репозитории, конфиге и переменных окружения паролей нет. Каталог профиля в `.gitignore`.
4. **`auth_required` — остановка.** Если адаптер видит, что сессия протухла, очередь встаёт и зовёт человека. Попыток восстановить сессию самостоятельно не делается.
5. **Kill switch.** Одна команда останавливает отправку и возвращает всё незавершённое в `approved`.
6. **`geekjob.ru` — только UI.** Внутренние `/json/` и `/rest/` закрыты в robots.txt прямым текстом и не используются.

## 7. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Адаптер упал на `search` | Логируем, остальные адаптеры продолжают. Частичный результат — валидный результат |
| Вакансия уже в БД | Молча пропускаем на стадии dedupe |
| LLM вернул ошибку или отказ | Запись уходит в очередь без письма, со статусом `pending` и пометкой. Человек видит её и может написать письмо руками |
| `apply` вернул `failed` | Статус `failed` + текст причины. Повторов автоматом нет — решение о повторе принимает человек |
| `apply` вернул `already_applied` | Статус `sent`, дедуп-таблица дополняется |
| Капча или `auth_required` | Остановка всей очереди, уведомление |
| Процесс убит посреди отправки | При старте все `approved` без `sent_at` считаются неотправленными и обрабатываются заново. Дубль невозможен из-за уникального индекса |

## 8. Тестирование

Разработка по TDD.

- **`scorer`** — чистая функция. Табличные тесты: набор вакансий с известным ожидаемым скором.
- **`queue`** — тесты на дедупликацию, на восстановление после обрыва, на корректность переходов статусов.
- **`letter`** — LLM мокается. Проверяется сборка промпта: порядок блоков (стабильное перед волатильным), выбор режима по порогу, выбор скелета и языка.
- **`adapters`** — тесты против сохранённых HTML-страниц и записанных HTTP-ответов. Живой сети в тестах нет.
- **Живая проверка** — отдельный ручной шаг: один отклик на одну реальную вакансию с каждой площадки, под наблюдением. Автотесты в продакшен-аккаунт не ходят никогда.
- **`sender`** — тесты на троттлинг (счётчики, паузы) и на остановку по капче.

## 9. Что проверяется в первую очередь

Первая итерация существует ради одной проверки: **выдержит ли интерфейс `Adapter` две крайности** — браузерный `hh.ru` с UI-откликом и чистый HTTP `hr.ge` с публичным API. Если для одного из них придётся протаскивать сквозь ядро что-то специальное, интерфейс спроектирован неверно и правится до того, как появятся ещё четыре адаптера.
